## 2026-09-08 20:05 — Выбор стека

**Решили.**

| Слой | Выбор |
| --- | --- |
| Backend | Python 3.12, FastAPI, SQLAlchemy 2 (async), Alembic |
| База | PostgreSQL 16 |
| Frontend | React + Vite, карта — react-leaflet поверх OpenStreetMap |
| Запуск | docker-compose: `postgres`, `backend`, `frontend` |
| Качество | pytest + ruff на бэке, ESLint + сборка на фронте, CI в GitHub Actions |

**Почему.**

- Продукт клиент-серверный с отдельным фронтом и бэком, общающимися по сети, и реляционной базой — это
  требование задания, стек подобран под него.
- **FastAPI** даёт async из коробки, типизацию через Pydantic и автоматическую OpenAPI-документацию; для
  сервиса с картой и частыми короткими запросами (позиции самокатов, старт/стоп аренды) это удобно.
- **SQLAlchemy 2 async + asyncpg** — единственный зрелый async-ORM для Postgres, стиль 2.0 с типизированными
  моделями хорошо ложится на Pydantic-схемы. **Alembic** — штатные миграции для SQLAlchemy.
- **PostgreSQL 16** — реляционная база по условию; при необходимости гео-запросов можно подключить PostGIS,
  на старте достаточно колонок lat/lon.
- **React + Vite** — быстрая сборка и dev-сервер, стандартный SPA-стек.
- **react-leaflet + OpenStreetMap** — бесплатные тайлы без API-ключей, ничего не нужно регистрировать,
  чтобы поднять проект «одной командой».
- **docker-compose** — единая команда `docker compose up --build` поднимает базу, бэкенд и фронтенд.

## 2026-09-09 18:50 — Почему nginx для фронтенда, и dev-режим с hot reload (ревью PR #1, п. 1)

**Почему в основном compose фронтенд отдаёт nginx, а не Vite dev server.**
- `docker compose up --build` — проверка «как в проде»: статическая сборка, тот же артефакт, что пойдёт
  в деплой. Dev-сервер не запускает `tsc -b`, и ошибки типов всплывали бы только в CI.
- nginx даёт один origin для SPA и API (прокси `/api`): без CORS, без второго порта; так же будет и
  в проде.
- Dev-сервер держит исходники и `node_modules` в контейнере и тратит ресурсы на watcher — ревьюеру
  и CI это не нужно.

Цена: при разработке фронта через прод-стек каждое изменение требует пересборки образа —
замечание из ревью.

**Решение: overlay `docker-compose.dev.yml`**
(`docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build`):
- frontend: стадия `dev` в Dockerfile (node + зависимости, без сборки), Vite dev server на 5173 с HMR,
  исходники примонтированы (`./frontend:/app`), `node_modules` контейнера защищён анонимным томом
  (у хоста другие нативные бинарники), `/api` проксируется на `backend:8000`;
- backend: `uvicorn --reload`, примонтированы `app/` и `alembic/`;
- watcher'ы в режиме polling (`VITE_WATCH_POLLING`, `WATCHFILES_FORCE_POLLING`): события inotify не
  проходят через bind mount с Windows/macOS-хоста;
- порт dev-сервера фиксирован (5173): HMR-клиент Vite подключается к порту страницы, при пробросе
  на другой порт HMR ломается.

Проверено: правка `App.tsx` на хосте → `[vite] hmr update /src/App.tsx`; правка `health.py` →
`WatchFiles detected changes ... Reloading`, health после перезапуска отвечает.

**Рассмотренные альтернативы.**
- `docker-compose.override.yml` (подхватывается автоматически) — сделал бы dev-режим режимом
  по умолчанию, и `docker compose up --build` перестал бы быть прод-проверкой. Отклонено.
- Профиль `dev` с отдельным сервисом `frontend-dev` — два фронтенда в одном стеке и путаница
  с портами. Отклонено.
- Только README с `npm run dev` — рабочий минимум, но hot reload бэкенда в Docker всё равно нужен,
  а одна команда на весь стек удобнее. Оставлено как альтернатива в README.

## 2026-09-09 18:50 — План тестов с настоящей базой (ревью PR #1, п. 2)

Сейчас `tests/test_db.py` проверяет только, что `get_db` отдаёт `AsyncSession` без подключения —
это smoke на wiring, а не на работу с базой. Когда появятся модели и брони, делаем так:

1. **Только настоящий PostgreSQL**, без подмены на SQLite: диалект asyncpg, типы (`timestamptz`,
   `numeric`, enum), ограничения и миграции должны проверяться на том же движке, что в проде.
2. **Откуда база.** Локально — сервис `db` из compose (`docker compose up -d db`), отдельная база
   `scooter_test` на том же сервере. В CI — `services: postgres:16` в job `backend` (штатная
   возможность GitHub Actions, без Docker-in-Docker). Настройки — те же `POSTGRES_*`, имя тестовой
   базы — `POSTGRES_TEST_DB` (по умолчанию `<POSTGRES_DB>_test`).
3. **Схема.** Session-фикстура создаёт тестовую базу (если её нет) и прогоняет
   `alembic upgrade head`; так миграции проверяются каждым прогоном. `Base.metadata.create_all`
   не используем — он может разойтись с миграциями. В конце сессии база дропается.
4. **Изоляция.** Каждый тест — в транзакции с откатом: соединение с `begin()`, сессия с
   `join_transaction_mode="create_savepoint"`, откат в teardown. Быстро (схема не пересоздаётся),
   тесты не видят данные друг друга. Зависимость `get_db` переопределяется через
   `app.dependency_overrides` на тестовую сессию — API-тесты идут через тот же httpx/ASGI-клиент.
5. **Маркировка.** Тесты с базой помечены `@pytest.mark.db`; `uv run pytest -m "not db"` — быстрый
   прогон без базы. Если база недоступна, db-тесты падают с понятной ошибкой, а не скипаются: иначе
   в CI легко не заметить, что они не выполнились.
6. **Тестовые данные.** Простые фикстуры-фабрики на SQLAlchemy без внешних библиотек, пока данных
   мало; `polyfactory` — если фабрики разрастутся.
7. **Readiness.** Вместе с первой моделью появится `GET /api/health/db` (`SELECT 1`); его тест —
   первый db-тест, он же заменит нынешний `test_db.py`.

Порядок внедрения: п. 2–3 вместе с первой миграцией (день 2), остальное — по мере появления моделей.

## 2026-09-09 19:15 — День 2: дизайн самокатов, телеметрии, реалтайма и симулятора

**Модель `scooters`.** `id` (int PK), `code` (уникальный, естественный ключ для телеметрии),
`lat`/`lon` (double precision — PostGIS для точек и радиусов пока не нужен), `battery` (smallint,
check 0..100), `status` (PG enum `scooter_status`: `available`, `reserved`, `riding`, `unavailable`),
`updated_at` (timestamptz, выставляет сервер).

**Правило заряда.** Порог `LOW_BATTERY_THRESHOLD` (по умолчанию 15) в настройках. Телеметрия с
зарядом ниже порога всегда переводит самокат в `unavailable`.
**Допущение:** обратный переход — если самокат `unavailable`, а телеметрия принесла заряд не ниже
порога, он снова `available` (у модели нет «причины недоступности», а без обратного перехода
симулятор за полчаса довёл бы весь парк до недоступного). `reserved`/`riding` телеметрия не трогает:
эти статусы появятся вместе с бронированием.
**Допущение:** сегодня движущиеся самокаты остаются «свободными» — телеметрия по условию несёт
только код, координаты и заряд. Выводить «в поездке» из факта движения отклонено: это смешивает
физику устройства с бизнес-состоянием (самокат могут везти на грузовике).

**Телеметрия.** `POST /api/telemetry` `{code, lat, lon, battery}` → 200 с актуальным состоянием
самоката (симулятор из ответа узнаёт статус), 404 для неизвестного кода, 422 при значениях вне
диапазонов.

**Реалтайм.** `GET /api/scooters` — начальное состояние; WebSocket `/api/ws` — после каждой
телеметрии сервер шлёт всем клиентам `{"type": "scooter.updated", "scooter": {...}}`. Клиент
открывает WS, потом делает GET, устаревшие данные отбрасывает по `updated_at` — так гонка между
GET и первым сообщением не теряет обновлений. Хаб соединений in-process: uvicorn с одним воркером;
для нескольких воркеров понадобится Redis pub/sub — отложено, записано как ограничение.
nginx и Vite проксируют Upgrade для `/api/ws`.

**Сид.** 18 самокатов в центре Бишкека, идемпотентный (только в пустую таблицу), в compose
запускается после `alembic upgrade head`. Два самоката с зарядом ниже порога — правило видно сразу
после запуска.

**Симулятор.** Отдельный сервис `simulator` (пакет `scootersim`, httpx, uv). Состояние на стороне
симулятора: `idle` / `riding` / `charging`; едущий двигается к случайной точке в bbox города, заряд
падает пропорционально пути; самокат, ставший `unavailable`, «заряжает техник» через
`SIM_RECHARGE_SECONDS`, и телеметрия возвращает его в строй. Скорость и расход завышены ради
наглядности демо (`SIM_SPEED_KMH=40`, `SIM_DRAIN_PER_KM=4`) — всё через env. Устойчивость: любые
ошибки HTTP → лог, пауза с backoff, повтор; процесс не завершается.

**Фронтенд.** Маркеры — `CircleMarker` (без возни с иконками Leaflet в бандлере), цвет по статусу,
попап с кодом, зарядом и статусом, легенда и счётчик в шапке, индикатор соединения, реконнект WS
с backoff. Для чистой логики (слияние обновлений, цвета) — vitest. Центр карты сдвинут в центр bbox
симулятора (42.875, 74.600), zoom 14, чтобы движение было заметно.

**Тесты.** По плану от 2026-09-09 18:50: реальный PostgreSQL, база `<POSTGRES_DB>_test`,
`alembic upgrade head` в session-фикстуре, транзакция с откатом на тест, `dependency_overrides`
для `get_db`, маркер `db`, в CI — `services: postgres:16`. Первый db-тест — readiness
`GET /api/health/db`.

**Объём.** Этап большой, но критерии приёмки сквозные (карта живёт только со всеми частями), поэтому

## 2026-09-09 19:44 — День 2: решения по ходу реализации

- **`updated_at` = `clock_timestamp()`**, а не `now()`: `now()` в PostgreSQL — время начала
  транзакции, и два обновления в одной транзакции получили бы одинаковое время. Фронтенд отбрасывает
  устаревшие сообщения по `updated_at`, поэтому нужно реальное время записи.
- **Naming convention** для ограничений в `Base.metadata` (`ck_…`, `uq_…`, `pk_…`), чтобы миграции
  могли ссылаться на них по имени.
- **Тестовая база.** Session-фикстура пересоздаёт `<POSTGRES_DB>_test` (`DROP … WITH (FORCE)` +
  `CREATE`) и прогоняет миграции через Alembic, которому URL передаётся через `config.attributes`.
  Тесты с фикстурой `db_session` получают маркер `db` автоматически. Если база недоступна, они падают
  с подсказкой `docker compose up -d db`, а не скипаются.
- **Локальный конфликт портов.** На машине разработки порт 5432 занят нативным PostgreSQL 17,
  5433 — базой другого проекта, 55432 попал в зарезервированный Windows диапазон (WinNAT).
  Compose-база опубликована на 15432 через локальный `.env` (`POSTGRES_PORT=15432`, файл в
  gitignore); бэкенд и тесты читают тот же `.env`. Для README добавлена подсказка про смену порта.
  Сам конфликт показал, что вынос порта в настройки был правильным решением.
- **WebSocket-хаб** живёт в процессе; тест самого эндпоинта — через `TestClient` Starlette
  (broadcast вызывается через его portal). Два deprecation-предупреждения внутри `TestClient`
  отфильтрованы в конфиге pytest как чужие.
- **Симулятор** — синхронный httpx: до двух десятков запросов раз в 1.5 с не требуют асинхронности.
  Backoff 1 → 2 → 4 … → 30 с; 404 по коду самоката означает, что парк изменился — список перечитывается.
  Самокат, который бэкенд вернул как `unavailable`, симулятор переводит в «зарядку» и через
  `SIM_RECHARGE_SECONDS` возвращает с зарядом 85–100 %. Пауза по умолчанию поднята с 60 до 180 с,
  чтобы серые маркеры из сида были видны ревьюеру дольше первой минуты.
- **Фронтенд.** vitest 5 для чистой логики (слияние обновлений, метаданные статусов), без
  DOM-тестов: компоненты — тонкие обёртки над react-leaflet, их проверяет сквозной прогон в Docker.
  После каждого открытия WebSocket список перечитывается через GET — так восстанавливается состояние
  после разрыва без отдельного протокола снапшотов.
- **Процесс.** Очень длинные команды Bash (сотни строк с несколькими heredoc) дважды не
  распарсились; большие файлы теперь пишутся через инструмент записи файлов, Bash — для команд.

## 2026-09-10 18:36 — Ревью PR #2: разрядка в поездке, ресинк после реконнекта, движение по прямой

**1. Заряд ниже порога во время поездки или брони.** Сейчас `status_after_telemetry` переводит
самокат в `unavailable` при любом текущем статусе. По заданию разрядка во время поездки должна
завершать поездку со счётом и письмом пользователю, а не просто менять статус. Пока поездок нет,
правило оставлено как есть; в коде стоит `TODO(rides)`, пункт добавлен в раздел «Что дальше» README.
Реализуется на этапе поездок: телеметрия ниже порога для `riding` → завершение поездки → счёт →
письмо → `unavailable`.

**2. Ресинк после переподключения WebSocket.** Уже реализовано: в `useScooterFeed` обработчик
`onopen` вызывает `GET /api/scooters` при каждом открытии сокета, включая переподключения, а
устаревшие данные отбрасываются по `updated_at`. События, потерянные за время разрыва, восполняются
целым списком. Проверено на живом стеке: `docker compose restart frontend` роняет WebSocket, клиент
показывает «Переподключение…», через ~0.9 с соединение восстановлено, счётчик запросов
`/api/scooters` на странице вырос с 1 до 2, маркеры двигаются. В access-логе nginx после каждого
реконнекта виден повторный `GET /api/scooters`. Кода не меняли.

**3. Движение по прямой.** Симулятор ведёт самокат по отрезку между случайными точками bbox и
проходит сквозь кварталы — осознанное упрощение: для демонстрации реалтайма важна динамика, а не
геометрия маршрута, а роутинг по дорогам стоит дорого (внешний сервис или граф дорог). Записано в
«Что дальше»: маршруты через OSRM (публичный демо-сервер или Docker-образ с выгрузкой OSM по
Кыргызстану) либо собственный граф дорог OSM через osmnx и путь по нему.

Заметка по процессу: при проверке выяснилось, что несколько вызовов инструментов в одном шаге
выполняются последовательно, поэтому «перезапуск во время ожидания» нужно запускать фоновым
процессом; первый замер из-за этого не увидел разрыва.
