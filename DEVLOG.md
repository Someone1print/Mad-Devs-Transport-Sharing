## 2026-09-08 20:05 — Выбор стека

**Решили.**

| Слой | Выбор |
| --- | --- |
| Backend | Python 3.12, FastAPI, SQLAlchemy 2 (async), Alembic |
| База | PostgreSQL 16 |
| Frontend | React + Vite, карта — react-leaflet поверх OpenStreetMap |
| Запуск | docker-compose: `postgres`, `backend`, `frontend` |
| Качество | pytest + ruff на бэке, ESLint + сборка на фронте, CI в GitHub Actions |

**Почему.**

- Продукт клиент-серверный с отдельным фронтом и бэком, общающимися по сети, и реляционной базой — это
  требование задания, стек подобран под него.
- **FastAPI** даёт async из коробки, типизацию через Pydantic и автоматическую OpenAPI-документацию; для
  сервиса с картой и частыми короткими запросами (позиции самокатов, старт/стоп аренды) это удобно.
- **SQLAlchemy 2 async + asyncpg** — единственный зрелый async-ORM для Postgres, стиль 2.0 с типизированными
  моделями хорошо ложится на Pydantic-схемы. **Alembic** — штатные миграции для SQLAlchemy.
- **PostgreSQL 16** — реляционная база по условию; при необходимости гео-запросов можно подключить PostGIS,
  на старте достаточно колонок lat/lon.
- **React + Vite** — быстрая сборка и dev-сервер, стандартный SPA-стек.
- **react-leaflet + OpenStreetMap** — бесплатные тайлы без API-ключей, ничего не нужно регистрировать,
  чтобы поднять проект «одной командой».
- **docker-compose** — единая команда `docker compose up --build` поднимает базу, бэкенд и фронтенд.

## 2026-09-09 18:50 — Почему nginx для фронтенда, и dev-режим с hot reload (ревью PR #1, п. 1)

**Почему в основном compose фронтенд отдаёт nginx, а не Vite dev server.**
- `docker compose up --build` — проверка «как в проде»: статическая сборка, тот же артефакт, что пойдёт
  в деплой. Dev-сервер не запускает `tsc -b`, и ошибки типов всплывали бы только в CI.
- nginx даёт один origin для SPA и API (прокси `/api`): без CORS, без второго порта; так же будет и
  в проде.
- Dev-сервер держит исходники и `node_modules` в контейнере и тратит ресурсы на watcher — ревьюеру
  и CI это не нужно.

Цена: при разработке фронта через прод-стек каждое изменение требует пересборки образа —
замечание из ревью.

**Решение: overlay `docker-compose.dev.yml`**
(`docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build`):
- frontend: стадия `dev` в Dockerfile (node + зависимости, без сборки), Vite dev server на 5173 с HMR,
  исходники примонтированы (`./frontend:/app`), `node_modules` контейнера защищён анонимным томом
  (у хоста другие нативные бинарники), `/api` проксируется на `backend:8000`;
- backend: `uvicorn --reload`, примонтированы `app/` и `alembic/`;
- watcher'ы в режиме polling (`VITE_WATCH_POLLING`, `WATCHFILES_FORCE_POLLING`): события inotify не
  проходят через bind mount с Windows/macOS-хоста;
- порт dev-сервера фиксирован (5173): HMR-клиент Vite подключается к порту страницы, при пробросе
  на другой порт HMR ломается.

Проверено: правка `App.tsx` на хосте → `[vite] hmr update /src/App.tsx`; правка `health.py` →
`WatchFiles detected changes ... Reloading`, health после перезапуска отвечает.

**Рассмотренные альтернативы.**
- `docker-compose.override.yml` (подхватывается автоматически) — сделал бы dev-режим режимом
  по умолчанию, и `docker compose up --build` перестал бы быть прод-проверкой. Отклонено.
- Профиль `dev` с отдельным сервисом `frontend-dev` — два фронтенда в одном стеке и путаница
  с портами. Отклонено.
- Только README с `npm run dev` — рабочий минимум, но hot reload бэкенда в Docker всё равно нужен,
  а одна команда на весь стек удобнее. Оставлено как альтернатива в README.

## 2026-09-09 18:50 — План тестов с настоящей базой (ревью PR #1, п. 2)

Сейчас `tests/test_db.py` проверяет только, что `get_db` отдаёт `AsyncSession` без подключения —
это smoke на wiring, а не на работу с базой. Когда появятся модели и брони, делаем так:

1. **Только настоящий PostgreSQL**, без подмены на SQLite: диалект asyncpg, типы (`timestamptz`,
   `numeric`, enum), ограничения и миграции должны проверяться на том же движке, что в проде.
2. **Откуда база.** Локально — сервис `db` из compose (`docker compose up -d db`), отдельная база
   `scooter_test` на том же сервере. В CI — `services: postgres:16` в job `backend` (штатная
   возможность GitHub Actions, без Docker-in-Docker). Настройки — те же `POSTGRES_*`, имя тестовой
   базы — `POSTGRES_TEST_DB` (по умолчанию `<POSTGRES_DB>_test`).
3. **Схема.** Session-фикстура создаёт тестовую базу (если её нет) и прогоняет
   `alembic upgrade head`; так миграции проверяются каждым прогоном. `Base.metadata.create_all`
   не используем — он может разойтись с миграциями. В конце сессии база дропается.
4. **Изоляция.** Каждый тест — в транзакции с откатом: соединение с `begin()`, сессия с
   `join_transaction_mode="create_savepoint"`, откат в teardown. Быстро (схема не пересоздаётся),
   тесты не видят данные друг друга. Зависимость `get_db` переопределяется через
   `app.dependency_overrides` на тестовую сессию — API-тесты идут через тот же httpx/ASGI-клиент.
5. **Маркировка.** Тесты с базой помечены `@pytest.mark.db`; `uv run pytest -m "not db"` — быстрый
   прогон без базы. Если база недоступна, db-тесты падают с понятной ошибкой, а не скипаются: иначе
   в CI легко не заметить, что они не выполнились.
6. **Тестовые данные.** Простые фикстуры-фабрики на SQLAlchemy без внешних библиотек, пока данных
   мало; `polyfactory` — если фабрики разрастутся.
7. **Readiness.** Вместе с первой моделью появится `GET /api/health/db` (`SELECT 1`); его тест —
   первый db-тест, он же заменит нынешний `test_db.py`.

Порядок внедрения: п. 2–3 вместе с первой миграцией (день 2), остальное — по мере появления моделей.

## 2026-09-09 19:15 — День 2: дизайн самокатов, телеметрии, реалтайма и симулятора

**Модель `scooters`.** `id` (int PK), `code` (уникальный, естественный ключ для телеметрии),
`lat`/`lon` (double precision — PostGIS для точек и радиусов пока не нужен), `battery` (smallint,
check 0..100), `status` (PG enum `scooter_status`: `available`, `reserved`, `riding`, `unavailable`),
`updated_at` (timestamptz, выставляет сервер).

**Правило заряда.** Порог `LOW_BATTERY_THRESHOLD` (по умолчанию 15) в настройках. Телеметрия с
зарядом ниже порога всегда переводит самокат в `unavailable`.
**Допущение:** обратный переход — если самокат `unavailable`, а телеметрия принесла заряд не ниже
порога, он снова `available` (у модели нет «причины недоступности», а без обратного перехода
симулятор за полчаса довёл бы весь парк до недоступного). `reserved`/`riding` телеметрия не трогает:
эти статусы появятся вместе с бронированием.
**Допущение:** сегодня движущиеся самокаты остаются «свободными» — телеметрия по условию несёт
только код, координаты и заряд. Выводить «в поездке» из факта движения отклонено: это смешивает
физику устройства с бизнес-состоянием (самокат могут везти на грузовике).

**Телеметрия.** `POST /api/telemetry` `{code, lat, lon, battery}` → 200 с актуальным состоянием
самоката (симулятор из ответа узнаёт статус), 404 для неизвестного кода, 422 при значениях вне
диапазонов.

**Реалтайм.** `GET /api/scooters` — начальное состояние; WebSocket `/api/ws` — после каждой
телеметрии сервер шлёт всем клиентам `{"type": "scooter.updated", "scooter": {...}}`. Клиент
открывает WS, потом делает GET, устаревшие данные отбрасывает по `updated_at` — так гонка между
GET и первым сообщением не теряет обновлений. Хаб соединений in-process: uvicorn с одним воркером;
для нескольких воркеров понадобится Redis pub/sub — отложено, записано как ограничение.
nginx и Vite проксируют Upgrade для `/api/ws`.

**Сид.** 18 самокатов в центре Бишкека, идемпотентный (только в пустую таблицу), в compose
запускается после `alembic upgrade head`. Два самоката с зарядом ниже порога — правило видно сразу
после запуска.

**Симулятор.** Отдельный сервис `simulator` (пакет `scootersim`, httpx, uv). Состояние на стороне
симулятора: `idle` / `riding` / `charging`; едущий двигается к случайной точке в bbox города, заряд
падает пропорционально пути; самокат, ставший `unavailable`, «заряжает техник» через
`SIM_RECHARGE_SECONDS`, и телеметрия возвращает его в строй. Скорость и расход завышены ради
наглядности демо (`SIM_SPEED_KMH=40`, `SIM_DRAIN_PER_KM=4`) — всё через env. Устойчивость: любые
ошибки HTTP → лог, пауза с backoff, повтор; процесс не завершается.

**Фронтенд.** Маркеры — `CircleMarker` (без возни с иконками Leaflet в бандлере), цвет по статусу,
попап с кодом, зарядом и статусом, легенда и счётчик в шапке, индикатор соединения, реконнект WS
с backoff. Для чистой логики (слияние обновлений, цвета) — vitest. Центр карты сдвинут в центр bbox
симулятора (42.875, 74.600), zoom 14, чтобы движение было заметно.

**Тесты.** По плану от 2026-09-09 18:50: реальный PostgreSQL, база `<POSTGRES_DB>_test`,
`alembic upgrade head` в session-фикстуре, транзакция с откатом на тест, `dependency_overrides`
для `get_db`, маркер `db`, в CI — `services: postgres:16`. Первый db-тест — readiness
`GET /api/health/db`.

**Объём.** Этап большой, но критерии приёмки сквозные (карта живёт только со всеми частями), поэтому
делаю одним PR с мелкими коммитами в порядке: тестовая инфраструктура → модель и миграция → сид →

## 2026-09-09 19:44 — День 2: решения по ходу реализации

- **`updated_at` = `clock_timestamp()`**, а не `now()`: `now()` в PostgreSQL — время начала
  транзакции, и два обновления в одной транзакции получили бы одинаковое время. Фронтенд отбрасывает
  устаревшие сообщения по `updated_at`, поэтому нужно реальное время записи.
- **Naming convention** для ограничений в `Base.metadata` (`ck_…`, `uq_…`, `pk_…`), чтобы миграции
  могли ссылаться на них по имени.
- **Тестовая база.** Session-фикстура пересоздаёт `<POSTGRES_DB>_test` (`DROP … WITH (FORCE)` +
  `CREATE`) и прогоняет миграции через Alembic, которому URL передаётся через `config.attributes`.
  Тесты с фикстурой `db_session` получают маркер `db` автоматически. Если база недоступна, они падают
  с подсказкой `docker compose up -d db`, а не скипаются.
- **Локальный конфликт портов.** На машине разработки порт 5432 занят нативным PostgreSQL 17,
  5433 — базой другого проекта, 55432 попал в зарезервированный Windows диапазон (WinNAT).
  Compose-база опубликована на 15432 через локальный `.env` (`POSTGRES_PORT=15432`, файл в
  gitignore); бэкенд и тесты читают тот же `.env`. Для README добавлена подсказка про смену порта.
  Сам конфликт показал, что вынос порта в настройки был правильным решением.
- **WebSocket-хаб** живёт в процессе; тест самого эндпоинта — через `TestClient` Starlette
  (broadcast вызывается через его portal). Два deprecation-предупреждения внутри `TestClient`
  отфильтрованы в конфиге pytest как чужие.
- **Симулятор** — синхронный httpx: до двух десятков запросов раз в 1.5 с не требуют асинхронности.
  Backoff 1 → 2 → 4 … → 30 с; 404 по коду самоката означает, что парк изменился — список перечитывается.
  Самокат, который бэкенд вернул как `unavailable`, симулятор переводит в «зарядку» и через

- **Фронтенд.** vitest 5 для чистой логики (слияние обновлений, метаданные статусов), без

  После каждого открытия WebSocket список перечитывается через GET — так восстанавливается состояние

- **Процесс.** Очень длинные команды Bash (сотни строк с несколькими heredoc) дважды не
  распарсились; большие файлы теперь пишутся через инструмент записи файлов, Bash — для команд.

## 2026-09-10 18:51 — День 3: дизайн пользователей и бронирования, допущения

**Пользователи без паролей.** Задание оставляет вход на наше усмотрение, а главный риск этапа —
конкурентное бронирование, поэтому силы идут туда. Пользователь при первом заходе вводит имя,
`POST /api/users` создаёт запись и возвращает `id`; фронтенд хранит `id` и имя в localStorage и
передаёт `id` в заголовке `X-User-Id`. `GET /api/users/me` проверяет сохранённый `id` при загрузке:
после сброса базы фронтенд получит 401 и снова спросит имя. Аутентификации и авторизации нет — любой,
кто знает `id`, действует от имени пользователя; это осознанное ограничение демо, записано в «Что
дальше».

**Модель брони.** `bookings`: `user_id`, `scooter_id`, `status` (`active` / `cancelled` / `expired`),
`created_at`, `expires_at`, `warned_at`, `ended_at`. Активная бронь держит самокат в статусе
`reserved`; `expires_at = created_at + BOOKING_TTL_SECONDS` (по умолчанию 900).

**Гонка за самокат — защита на уровне базы.** В одной транзакции: `SELECT … FOR UPDATE` строки
пользователя (сериализует его собственные попытки), затем `SELECT … FOR UPDATE` строки самоката —
второй параллельный запрос ждёт на блокировке, после коммита первого перечитывает строку, видит
`reserved` и получает 409. Страховка — частичные уникальные индексы `bookings(scooter_id) WHERE
status = 'active'` и `bookings(user_id) WHERE status = 'active'`: даже если логика где-то ошибётся,
второй активной брони на самокат или пользователя база не примет (IntegrityError → 409). Блокировки
берутся всегда в порядке «пользователь → самокат», чтобы исключить взаимные блокировки.
Ошибки 409 несут машинный код (`scooter_not_available`, `user_has_active_booking`) и текст;
фронтенд показывает понятное сообщение по коду.

**Таймеры в базе, а не в памяти.** Автоснятие и уведомление — по `expires_at`. Фоновая задача
(`asyncio`-таск в lifespan приложения) раз в `BOOKING_SWEEP_INTERVAL_SECONDS` (2 с) делает две
вещи: переводит активные брони с `expires_at <= now` в `expired` и возвращает самокат в `available`
(если он всё ещё `reserved`); для активных броней с `expires_at <= now + BOOKING_WARN_BEFORE_SECONDS`
(180 с) и пустым `warned_at` атомарно выставляет `warned_at` (`UPDATE … WHERE warned_at IS NULL
RETURNING`) и только для затронутых строк шлёт уведомление. После перезапуска бэкенда состояние
целиком в базе: первая итерация после старта доснимает просроченное и дошлёт неотправленные
предупреждения. Строки берутся `FOR UPDATE SKIP LOCKED` — при нескольких воркерах итерации не
обработают одну бронь дважды.

**Уведомление ровно один раз.** Дедупликация держится на `warned_at`: оно персистентно (переживает
перезапуск) и меняется атомарным UPDATE (переживает параллельные итерации). Доставка через WebSocket
без подтверждения: если пользователь офлайн, событие теряется, но фронтенд при загрузке и
реконнекте перечитывает `GET /api/bookings/active` и сам показывает баннер, когда осталось меньше
`BOOKING_WARN_BEFORE_SECONDS`. Так уведомление не приходит дважды, а пропасть насовсем не может.

**Адресные события по WebSocket.** Заголовок в WebSocket из браузера не поставить, поэтому после
открытия сокета клиент шлёт `{"type": "identify", "user_id": N}`; хаб помнит соответствие сокет →
пользователь и умеет `send_to_user` (во все вкладки пользователя). Публичные события
`scooter.updated` идут всем, как раньше; личные — `booking.created`, `booking.cancelled`,
`booking.expiring`, `booking.expired`.

**Забронированный самокат и симулятор.** Симулятор считает `reserved` и `unavailable` «припаркованными»:
не начинает для них поездки и останавливает текущую, если самокат забронировали в движении; статусы
он подхватывает из ответов на телеметрию и из периодического перечитывания списка
(`SIM_REFRESH_TICKS`, 10 тиков ≈ 15 с). **Допущение:** едущий в симуляторе самокат на сервере
по-прежнему `available` (телеметрия статус не несёт, см. день 2), поэтому его можно забронировать
«на ходу» — симулятор остановит его в течение одного цикла обновления. С появлением поездок статус
`riding` закроет этот зазор.

**Фронтенд.** Экран с именем при первом заходе; `X-User-Id` во всех запросах бронирования;
в попапе свободного самоката кнопка «Забронировать», у своей брони таймер и «Отменить», чужая бронь —
жёлтый маркер с надписью; виджет «моя бронь» в шапке с обратным отсчётом; тосты для ошибок и событий,
заметный баннер за 3 минуты до снятия. Обратный отсчёт считается от `expires_at` по часам клиента —
**допущение:** расхождение часов клиента и сервера не компенсируется.

**Тесты.** Главный — конкурентный: несколько одновременных `POST /api/bookings` от разных
пользователей на один самокат через `asyncio.gather`, каждый запрос в собственной транзакции
(для этого теста `get_db` подменяется фабрикой сессий к тестовой базе с настоящими коммитами и
очисткой таблиц после). Отдельно: ожидание на блокировке строки (вторая транзакция не проходит,
пока первая держит `FOR UPDATE`), страховочный индекс, одна активная бронь на пользователя, отмена,
снятие по `expires_at`, предупреждение ровно один раз, «перезапуск» (бронь с прошедшим `expires_at`
доснимается первой итерацией), цикл фоновой задачи с коротким интервалом. Интервалы — через
настройки, тесты подставляют секунды вместо минут.

**Объём.** Один PR, коммиты: пользователи → модель и создание брони → отмена и активная бронь →
адресные события → фоновая задача → симулятор → фронтенд (пользователь) → фронтенд (бронь) →
документация.

## 2026-09-10 19:13 — День 3: решения по ходу реализации

- **Тесты гонки с настоящими транзакциями.** Обычная фикстура `db_session` держит один
  коннект и одну транзакцию с откатом — для гонки это бесполезно, все запросы попали бы в одну
  транзакцию. Добавлена фикстура `committed_db`: `get_db` подменяется фабрикой сессий к тестовой
  базе, каждый запрос получает свой коннект и настоящий коммит, после теста таблицы очищаются
  `TRUNCATE`. На ней три одновременных `POST /api/bookings` дают ровно один 201 и два 409, а
  отдельный тест держит `SELECT … FOR UPDATE` в чужой транзакции и проверяет, что запрос
  действительно ждёт снятия блокировки (не завершается 300 мс) и завершается после `COMMIT`.
- **Порядок блокировок.** Сначала строка пользователя, потом самоката — одинаковый порядок во всех
  операциях, чтобы исключить взаимные блокировки. Отмена и sweeper блокируют бронь
  (`FOR UPDATE OF bookings`, потому что бронь грузится join'ом с пользователем и самокатом) и
  самокат; sweeper — `SKIP LOCKED`, чтобы параллельная итерация не ждала.
- **Sweeper в lifespan приложения**, с флагом `BOOKING_SWEEPER_ENABLED`: в тестах цикл выключен,
  потому что lifespan `TestClient` поднимал бы его на dev-базе; сам цикл проверяется отдельным
  тестом с интервалом 50 мс на тестовой базе.
- **`GET /api/config`** отдаёт длительность брони и порог предупреждения: клиент показывает
  «Забронировать на 15 мин» и баннер по своим часам, не зашивая значения.
- **Идентичность во вкладке.** Пользователь хранится в `sessionStorage`, а не в `localStorage`:
  новая вкладка — новый пользователь, и сценарий приёмки «две вкладки под разными
  пользователями» работает без режима инкогнито; перезагрузка вкладки пользователя сохраняет.
  В шапке есть «сменить».
- **Пропущенное событие истечения.** Кроме серверного `booking.expired`, клиент через 3 с после
  `expires_at` сам перечитывает `GET /api/bookings/active` — если вкладка была офлайн, бронь
  всё равно исчезнет из интерфейса.
- **Ограничение (security review).** `identify` по WebSocket, как и заголовок `X-User-Id`,
  доверяет клиенту: любой, кто знает `id`, получит личные события и сможет действовать от имени
  пользователя. Это следствие решения «без паролей» на этот этап; при появлении входа
  и заголовок, и `identify` заменяются на сессионный токен.
- **Отладка тестов.** Дважды ловил `MissingGreenlet`: после `expire_all()`/`rollback()`
  обращение к атрибутам ORM-объектов в async-коде тянет ленивую загрузку — id фиксируются
  в переменные до сброса.

## 2026-09-10 20:53 — Ревью PR #3: короткие брони, точность таймеров, скриншоты

**1. Бронь короче трёх минут.** Как было: правило «предупредить, когда до снятия осталось меньше
`BOOKING_WARN_BEFORE_SECONDS`» срабатывало для 60-секундной брони на первой же итерации свипера —
через секунду после «забронировано» приходило «истекает через 00:59». Честно, но избыточно.
Решение: окно предупреждения = `min(BOOKING_WARN_BEFORE_SECONDS, длина брони / 2)`. Для
обычных 15-минутных броней это по-прежнему 3 минуты; 60-секундная бронь предупреждается за
30 секунд, а не при создании. Реализовано в SQL свипера (`LEAST(:warn, (expires_at -
created_at) / 2)`), баннер на клиенте считает то же окно по `created_at`/`expires_at`. Тест:
60-секундная бронь не предупреждается ни при создании, ни за 31 с, предупреждается за 29 с.
Демо-конфиг из README (`60 / 20 / 1`) поведения не меняет: `min(20, 30) = 20`.

**2. Точность таймеров.** Снятие и предупреждение выполняет фоновая задача с периодом
`BOOKING_SWEEP_INTERVAL_SECONDS` (по умолчанию 2 с, настраивается через `.env` и compose), поэтому
оба события опаздывают не более чем на один интервал плюс время запроса; в сквозной проверке
с интервалом 1 с бронь снялась через 1 с после `expires_at`. При падении бэкенда просроченные
брони снимаются первой итерацией после старта (задержка = время простоя). Обратный отсчёт в
интерфейсе считается по часам клиента от серверного `expires_at`, расхождение часов не
компенсируется; баннер появляется по клиентским часам, тост — по событию с сервера, поэтому
они могут разойтись на интервал свипера. Записано в README, раздел «Точность таймеров».

**3. Скриншоты.** В README добавлен раздел «Как это выглядит» с четырьмя кадрами из сквозных
проверок (`docs/images/*.jpg`, сжаты до ~250 КБ): карта с парком, своя бронь с отсчётом,
конфликт брони у второго пользователя, баннер за 20 секунд до снятия.

## 2026-09-12 14:38 — День 4: дизайн поездок, тарификации и зоны обслуживания, допущения

**Модель.** `rides`: `user_id`, `scooter_id`, `booking_id` (уникальный — из одной брони одна
поездка), `status` (`active` / `paused` / `finished`), `started_at`, `finished_at`, снимок тарифов
на момент старта (`ride_rate_per_minute`, `pause_rate_per_minute`, `NUMERIC(8,2)`) и итоги после
завершения (`ride_seconds`, `pause_seconds`, `ride_cost`, `pause_cost`, `total_cost`,
`NUMERIC(10,2)`). `ride_segments`: `ride_id`, `kind` (`ride` / `pause`), `started_at`, `ended_at`
(пусто у открытого сегмента), `seconds`, `cost` (заполняются при закрытии). Частичные уникальные
индексы `rides(user_id) WHERE status <> 'finished'` и `rides(scooter_id) WHERE status <> 'finished'`
— страховка «одна активная поездка на пользователя и на самокат». У брони появляется статус `used`
(конвертирована в поездку); сразу три-четыре значения enum меняются миграцией с `ALTER TYPE …
ADD VALUE`, откат пересоздаёт тип.
**Допущение:** тарифы фиксируются в поездке при старте — изменение настроек не меняет счёт
уже идущей поездки, а чек воспроизводим.

**Переходы и идемпотентность.** `POST /api/rides {booking_id}`: бронь должна быть своей и
активной; повторный старт по той же брони, когда её поездка ещё идёт, возвращает ту же поездку
с 200 (а не 409) — повтор клика или ретрай ничего не ломают. Старт по чужой брони — 403, по
истёкшей/отменённой — 409 `booking_not_active`. `pause` у уже стоящей и `resume` у уже едущей
поездки — 200 с текущим состоянием, `finish` завершённой — 200 с тем же чеком; переходы из
`finished` в `paused`/`active` — 409 `ride_finished`. Пока идёт поездка, новую бронь сделать нельзя
(409 `user_has_active_ride`).

**Блокировки.** Старт: `FOR UPDATE` пользователя → брони → самоката (тот же порядок «пользователь
→ самокат», что у бронирования; бронь — между ними, как в sweeper'е, где бронь блокируется раньше
самоката). Пауза/возобновление/завершение: `FOR UPDATE` поездки → самоката. Sweeper видит только
`active` брони, поэтому конвертированная бронь ему не интересна; если он успел снять бронь первым,
старт дождётся снятия блокировки, увидит `expired` и вернёт 409.

**Тарификация — правило округления.** Оплата посекундная, пропорциональная тарифу за минуту:
`cost = rate_per_minute × seconds / 60`, округление до копейки половиной вверх (`ROUND_HALF_UP`)
**для каждого сегмента отдельно**; секунды сегмента — целые, дробная часть отбрасывается в пользу
пользователя. Итог поездки **определяется** как сумма стоимостей сегментов, стоимость езды — сумма
сегментов `ride`, паузы — сумма `pause`; поэтому «сумма по сегментам = итог» выполняется по
построению, а тест проверяет это на случайных наборах сегментов (hypothesis) вместе с тем, что
каждая стоимость — `Decimal` с двумя знаками и отличается от точной пропорции не больше чем на
полкопейки. Почему не «поминутно вверх»: при нескольких коротких паузах каждая стоила бы полную
минуту, а «вверх» на агрегате по виду сегментов не сводится с посегментной разбивкой чека.
Деньги везде `Decimal` (`NUMERIC` в базе, строки в JSON), в настройках `RIDE_RATE_PER_MINUTE` и
`PAUSE_RATE_PER_MINUTE` (по умолчанию 5.00 и 1.50 сом).
Клиент считает текущую стоимость тем же правилом в целых копейках: `Math.round(rate_kopecks ×
seconds / 60)`. Для целых `rate_kopecks` и `seconds` точное значение — рациональное со знаменателем
60, поэтому либо это ровно `k + 0.5` (представимо точно, `Math.round` округляет вверх, как
`ROUND_HALF_UP`), либо отстоит от половины не меньше чем на 1/60 — ошибка float не может
перевернуть округление. Одни и те же тестовые векторы лежат в pytest и vitest.

**Зона обслуживания.** Таблица `service_zones` (`name`, `points` JSONB — список `{lat, lon}`),
одна зона «Центр Бишкека» (десятиугольник примерно 42.862–42.888 × 74.578–74.622), сидится вместе
с самокатами. `GET /api/zones` отдаёт список зон, карта рисует границу. Завершить поездку можно
только внутри зоны: проверяется **положение самоката из базы** (последняя телеметрия), а не
координаты из запроса — клиент их не подделает. Снаружи — 409 `outside_service_zone` с текстом
«Вы вне зоны обслуживания, вернитесь в зону, чтобы завершить поездку».
**Точка в полигоне без PostGIS** — лучевой алгоритм (even-odd) на чистом Python по координатам как
по плоскости: зона размером в несколько километров, кривизна Земли и различие масштабов широты и
долготы на таком размере не влияют на ответ, а точки на границе считаются внутренними (в пользу
пользователя). Почему так: PostGIS требует другой образ базы и GIS-типы ради одной проверки над
десятью вершинами; `shapely` — нативная зависимость ради той же функции. Тот же алгоритм на
TypeScript подсвечивает в панели поездки «в зоне / вне зоны» до нажатия «Завершить».

**Симулятор.** Самокаты со статусом `riding` едут (в том числе поездки пользователей): симулятор
ведёт их к случайным точкам в **зоне катания** `SIM_RIDE_BBOX`, которая шире зоны обслуживания

самокат стоит. Демо-поездки самих симулированных самокатов остаются в прежних границах и в квоту
`SIM_ACTIVE_SCOOTERS` едущие пользователями не входят.
**Допущение:** пока едущий самокат считается перемещаемым симулятором; телеметрию с телефона
пользователя в демо не делаем.

**API самокатов.** В `ScooterOut` добавляется `paused: bool` (есть ли поездка на паузе) —
симулятору, чтобы не двигать стоящий самокат, и попапу, чтобы показать «В поездке · пауза».

**Фронтенд.** В виджете брони кнопка «Начать поездку». Панель текущей поездки: код самоката,
состояние, время езды и паузы, текущая стоимость по тем же правилам (закрытые сегменты + открытый
по клиентским часам), индикатор «в зоне / вне зоны», кнопки «Пауза» / «Продолжить» / «Завершить».
Граница зоны на карте. При отказе 409 вне зоны — тост с сообщением сервера. По завершении —
модальный чек: ехал столько-то — столько сом, стоял столько-то — столько сом, итого.
**Допущение:** таймеры на клиенте считаются от серверных временных меток по клиентским часам,
расхождение часов не компенсируется (как у брони).

## 2026-09-12 21:03 — День 4: панель ревьюеров по дизайну и что она изменила

Перед реализацией дизайн прогнан через четыре независимые линзы (деньги, конкурентность,
продукт/приёмка, простота), каждая находка — через трёх скептиков, которые пытались её
опровергнуть по коду. Из 35 находок подтверждены (≥2 из 3 скептиков) и исправлены:

- **Разряд во время поездки.** Старое правило переводило `riding` в `unavailable` при заряде ниже
  порога, а «зарядка техником» в симуляторе через 3 минуты возвращала самокат в `available` —
  посреди чужой поездки его можно было забронировать, а `finish` затирал чужую бронь. Теперь
  `riding` для телеметрии «липкий»: заряд только записывается, правило порога применяется один раз
  при завершении (самокат остаётся `unavailable`, если заряд ниже порога). Правило дня 2 изменено,
  тест на `riding` переписан, `TODO(rides)` про автозавершение остаётся.
- **Потерянное обновление от телеметрии.** `apply_telemetry` читал строку без блокировки и писал
  статус, вычисленный по устаревшему снимку: телеметрия, ждавшая на блокировке `finish`, вернула бы
  `riding` поверх `available` навсегда. Теперь телеметрия берёт `FOR UPDATE` на самокат
  (сериализуется с переходами поездки; тест с удержанной блокировкой и коммитом `available`).
- **`now` раньше блокировки.** Пауза и завершение получают `now` до захвата строки; проигравший
  гонку запрос мог закрыть сегмент раньше его начала — `ValueError` и 500. Теперь после блокировки
  `now = max(now, started_at открытого сегмента)`: переупорядоченный запрос тарифицирует нулевой
  сегмент. Длительности — целочисленная арифметика `timedelta // 1s`, без float.
- **Старт по просроченной, но ещё не снятой sweeper'ом брони** — 409 `booking_not_active`
  по `expires_at <= now`, не дожидаясь sweeper'а.
- **`paused` — колонка `scooters`, а не `column_property`.** Пауза/возобновление/завершение пишут её
  под блокировкой строки самоката, поэтому `updated_at` растёт и клиент не отбросит событие паузы как
  устаревшее; в сериализацию флаг попадает через `from_attributes` без правок в шести местах.
- **Чек в базе.** `CHECK (total_cost = ride_cost + pause_cost)` на `rides`; тест сверяет сохранённые
  итоги с `SUM(cost)` по строкам сегментов в PostgreSQL, а не по ответу API.
- **Тарифы в настройках** ограничены тем, что точно хранит `NUMERIC(8,2)` (`max_digits=8`,
  `decimal_places=2`, `le=9999.99`): `5.005` или `1e7` отвергаются при старте, а не при поездке.
- **Копейки на клиенте.** Тариф из строки разбирается по строке (`"1.15" → 115`), а не через
  `Number(s) * 100` (=114.99999999999999); формула записана как `(rateKopecks * seconds) / 60`,
  порядок скобок несущий. В общие векторы добавлены ничьи (`1.50`/11 с → 0.28, `2.45`/30 с →
  1.23) и тариф, не точный во float (`1.15`/30 с → 0.58).
- **Симулятор узнавал о старте и возобновлении с опозданием до 15 с** (только из периодического
  обновления списка). Теперь удерживаемые самокаты (`reserved`, пауза) шлют телеметрию каждые
  `SIM_HELD_HEARTBEAT_TICKS` (3 с) и получают новый статус в ответе; в сквозной проверке самокат
  тронулся через 0.7 с после старта и через 2.4 с после возобновления.
- **Тексты ошибок.** Сервер отдаёт английский текст, как и остальные ошибки; русские формулировки
  живут на клиенте по коду (`outside_service_zone` и др.).
- **Свой самокат в поездке** сохраняет тёмную обводку, попап говорит «Ваша поездка», бронь других
  самокатов во время поездки отключена с пояснением; из баннера брони убрано «продлите бронь».
- **Пустой список зон** — завершение отказывает (закрыто по умолчанию), но бэкенд пишет
  предупреждение в лог: сид вставляет зону отдельно от самокатов, так что на старой базе с дня 3 она
  появится.

Отклонённые предложения — с причинами:
- *Убрать таблицу зон в пользу константы.* Задание просит хранить зону на бэке и отдавать через API;
  таблица делает зону данными, константа остаётся источником сида и тестов геометрии.
  Семантика «внутри любой из зон» и поведение при пустом списке записаны здесь и в README.
- *Не хранить стоимости сегментов и итоги.* Сохранённый чек — юридическая запись: он не изменится при
  смене правила округления или тарифов, а согласованность с сегментами гарантирует CHECK и тест.
- *Один bbox для симулятора.* Оставлены два: демо-поездки в прежнем, поездки пользователей в
  «чуть большем зоны» (см. ниже).
- *Убрать проверку точки на границе.* Оставлена как соглашение для вырожденных входов: полоса
  «границы» с порогом `1e-12` не наблюдаема на реальных координатах, и в DEVLOG она больше не
  подаётся как пользовательская гарантия.

Уточнения к записи о дизайне: `ALTER TYPE … ADD VALUE` нужен одному значению (`used`); типы
`ride_status` и `segment_kind` создаются с таблицами. Округление половиной вверх посегментно завышает
каждый сегмент не больше чем на полкопейки; отброшенная дробная секунда занижает его не больше чем на
`rate/60`, поэтому итог не выше точной пропорции плюс 0.005 × число сегментов. Позиция для проверки
зоны берётся из телеметрии самоката, а не из запроса на завершение; сама телеметрия пока не
аутентифицирована (см. «Что дальше» в README). `ride_seconds`/`pause_seconds` — суммы целых секунд
закрытых сегментов, панель считает время так же (сегменты сервера плюс открытый по клиентским
часам), а не `now − started_at`.

## 2026-09-12 21:03 — День 4: решения по ходу реализации

- **Время запросов через `app.core.clock.now()`**, а не `datetime.now()` на месте: тесты API
  подменяют часы и проверяют паузы и чеки с точными временными метками без ожидания.
- **Идемпотентный повтор не трогает самокат.** Второй `finish` и повторный `start` возвращают
  сохранённое состояние до блокировки самоката и ничего не рассылают; тест: между двумя `finish`
  другой пользователь бронирует самокат — бронь остаётся.
- **Гонка стартов.** Три одновременных `POST /api/rides` по одной брони — один 201 и два 200 с тем
  же id поездки (блокировка строки брони + уникальность `booking_id`).
- **Симулятор и зона — детерминированное демо.** Случайные цели давали непредсказуемое время
  до выезда из зоны (в первом прогоне — больше 5 минут ожидания возврата). Теперь поездка
  пользователя чередует леги: к внешней половине ближайшего края зоны катания (снаружи зоны
  обслуживания) кратчайшим путём, затем к ближайшей точке «глубокого ядра» (центральные 40 % зоны
  катания, целиком внутри зоны обслуживания с запасом ≈0.5 км; тест сверяет ядро с полигоном
  бэкенда). Замер на живом стеке: выезд через ~2 мин после старта, снаружи ~1 мин, внутри ~2.5 мин.
  Зона катания `RIDE_BBOX` = 42.856–42.894 × 74.570–74.630 (зона обслуживания занимает ~45 % её
  площади), демо-поездки самих самокатов остаются в прежнем `BISHKEK_BBOX`.
- **Ручной рычаг для проверяющего**: поставить поездку на паузу (самокат стоит) и отправить
  телеметрию с координатами внутри зоны — `POST /api/telemetry` с кодом самоката; следующая
  телеметрия симулятора придёт только через несколько секунд, завершить нужно сразу. Записано в README.
- **Позиция — у симулятора.** Симулятор не перечитывает координаты с сервера для известных
  самокатов, только статусы; ручная телеметрия «телепортирует» самокат до следующего тика.

## 2026-09-12 21:38 — День 4: ревью реализации и что оно изменило

Готовая ветка прогнана через вторую панель (деньги, паритет Python/TypeScript, конкурентность,
приёмка/фронтенд, симулятор) с теми же скептиками. Паритет тарификации подтверждён напрямую:
122 000 случайных пар «тариф × секунды» (включая 12 000 точных ничьих) и случайные многосегментные
поездки — Python и TypeScript совпали во всех случаях; посегментное округление сверено перебором
6 миллионов случаев с точной дробью. Найдено и исправлено:

- **Обнуление счёта частыми паузами** (блокер по деньгам, подтверждён воспроизведением: переключение
  каждые 0.9 с — 18.9 с поездки за 0.00). Секунды сегмента считались как floor его собственной длины,
  и каждый переход терял до секунды. Теперь секунды сегмента — разность целых секунд от начала
  поездки: остатки переносятся в следующий сегмент, сегменты в сумме дают `floor(длительность)`,
  за поездку теряется не больше одной секунды. Правило в DEVLOG выше и в README уточнено.
- **Регрессия симулятора** (блокер): ответ `available` на каждую телеметрию демо-поездки обрывал её,
  и самокаты симулятора дёргались по одному шагу за тик (в сквозной проверке смотрели только на
  самокат пользователя). Цель сбрасывается только у завершившейся поездки пользователя. Заодно: пауза
  сохраняет текущий лег (возобновление не разворачивает самокат), статус `riding`, пришедший посреди
  демо-поездки, начинает пользовательские леги заново.
- **Устаревший снимок под блокировкой** (major по конкурентности): `SELECT … FOR UPDATE` самоката
  возвращал объект, уже загруженный join'ом вместе с поездкой или бронью — до захвата блокировки.
  Завершение проверяло зону по старой позиции, старт и sweeper — по старому статусу. Теперь чтение под
  блокировкой идёт с `populate_existing`; тест: телеметрия увозит самокат из зоны, пока запрос на
  завершение уже загрузил поездку, — завершение отказывает.
- **`reserved` тоже липкий.** Телеметрия переводила забронированный самокат в `unavailable`, а потом в
  `available` при живой брони: держатель не мог стартовать («самокат available»), другие — забронировать
  (индекс). Теперь удерживаемые самокаты (`reserved`, `riding`) телеметрия не меняет; правило порога
  применяется при освобождении (отмена, снятие, завершение) и при старте (409 `scooter_battery_low`,
  бронь остаётся, её можно отменить). README согласован с кодом.
- **Фронтенд.** Виджет брони исчезал даже при неудачном старте (409/сеть) — теперь только при успехе;
  поездка и бронь перечитываются после реконнекта WebSocket и после 404/409 на действии; сообщение для
  `user_has_active_ride`; `parseMoney` сохраняет знак и игнорирует знаки после копейки.
- **Тарифы в настройках** квантуются до копеек: `RIDE_RATE_PER_MINUTE=5` отдаётся как `"5.00"`.
- **Ручной рычаг в README** гонялся с heartbeat стоящего самоката (3 с): теперь рецепт — остановить
  симулятор, отправить телеметрию, завершить, запустить симулятор.

копия помечена).

## 2026-09-12 22:54 — Ревью PR #4: паритет счёта и граница зоны

**1. Паритет клиента и сервера.** Честный ответ: 122 000 пар — разовый прогон агента ревью;
постоянными были только 17 общих векторов, продублированных в pytest и vitest, и hypothesis на

TypeScript с тем же файлом. Изменение правила на любой стороне ломает тест, а не расходится молча;
после осознанного изменения файл перегенерируют командой из докстринга. Дублирующиеся ручные
векторы в `test_billing.py` и `billing.test.ts` оставлены: они читаются как спецификация.

**2. Точка ровно на границе.** Правило: внутри. Алгоритм сначала проверяет попадание на ребро
(вершина, середина ребра, любая точка на нём) по векторному произведению с допуском
`BOUNDARY_EPS = 1e-12` градусов² — для рёбер зоны длиной ~1.5 км это полоса около 10 мкм, — и
только потом применяет чётность пересечений с полуоткрытым сравнением по долготе (попадание луча в
вершину считается один раз). Детерминированность: Python и TypeScript выполняют одни и те же операции
над IEEE-double в одном порядке, поэтому ответ побитово одинаков; общий набор кейсов пинит все 10
вершин и 10 середин рёбер зоны как «внутри» плюс 200 случайных точек. Практически телеметрия
с метровой точностью в полосу 10 мкм не попадёт, так что правило — про предсказуемость, а не про
пользу пользователю. Константа теперь названа в обоих файлах, правило записано в README.

## 2026-09-12 23:18 — День 5: дизайн почты-заглушки и кабинета, допущения

**Почта — заглушка в базе.** Таблица `emails`: `user_id`, `to_address`, `subject`, `body`,
`dedup_key` (уникальный), `created_at`. Внешнего SMTP нет — по заданию достаточно; письмо
«доставлено», когда строка вставлена, и его видно в интерфейсе.
**Допущение: адрес.** Пользователи регистрируются по имени, e-mail нет, поэтому `to_address`
выводится из имени: `<slug имени>@example.invalid` (зона `.invalid` по RFC 2606 никуда не
доставляется). Поле хранится, чтобы модель письма была честной и при появлении e-mail у
пользователя ничего не менять.

**Ровно одно письмо на ключ.** `send_email(session, user, subject, body, dedup_key)` делает
`INSERT … ON CONFLICT (dedup_key) DO NOTHING RETURNING id`: атомарно на уровне базы, как
`UPDATE … WHERE warned_at IS NULL` у броней. Повтор с тем же ключом возвращает `None`, письмо не
дублируется ни при повторном вызове, ни при гонке двух одновременных запросов. Ключ письма о поездке —
`ride:{id}:receipt`. Тесты: двойной вызов сервиса; двойное завершение через API; одновременные
завершения через `asyncio.gather` на настоящей базе.

**Когда отправлять.** Внутри `finish_ride`, в той же транзакции, что и чек (после расчёта,
до `commit`): либо и чек, и письмо, либо ничего; идемпотентный повтор `finish` до этой ветки не
доходит. Текст письма собирается из сохранённых колонок чека (`ride_seconds`, `pause_seconds`,
`ride_cost`, `pause_cost`, `total_cost`) — те же значения, что в ответе API.

**API.** `GET /api/emails` — письма текущего пользователя, новые сверху. `GET /api/rides` —
история поездок пользователя (завершённые, новые сверху, с чеком и сегментами) плюс текущая
отдельным полем; для кабинета и текущая поездка, и история отдаются одним запросом
`GET /api/account`: `{user, active_ride, rides, emails_count}`? — **решение:** три простых
эндпоинта (`/api/users/me`, `/api/rides/active`, `/api/rides`, `/api/emails`), без агрегата: меньше
связности, кабинет делает два запроса. Личное событие `email.sent` по WebSocket, чтобы счётчик
в шапке обновлялся без перезагрузки.

**Кабинет и почта на фронте.** Без роутера: панель-оверлей поверх карты, вкладки «Поездки» и
«Почта», открывается из шапки; в шапке — счётчик непрочитанных писем (непрочитанность — локально,
по последнему просмотренному id, сервер не хранит). Деньги в кабинете и в письмах — строки с
сервера как есть (`formatMoney(parseMoney(s))` только для единообразия вида «7.50», без
арифметики); текущая поездка в кабинете показывает живую оценку панели, помеченную как оценку, а
завершённые — только чек сервера.

**Объём.** Один PR: модель и миграция → сервис почты → письмо при завершении → история поездок →
события → фронт (кабинет, почта) → документация.

## 2026-09-12 23:34 — День 5: что вышло при реализации и сквозная проверка

**Отправка не коммитит.** `send_email` только вставляет строку и возвращает `Email | None`;
транзакцией владеет вызывающий. Первый вариант теста «пять одновременных отправок с одним ключом»
показал пять «успехов» — потому что ни одна сессия не коммитила, и `ON CONFLICT` не с чем было
конфликтовать. Тест переписан: каждая попытка коммитит, база оставляет одну строку. Само правило
не менялось, поменялось понимание: дедупликация срабатывает на коммите первого, остальные ждут
на уникальном индексе и получают `DO NOTHING`.

**Письмо в транзакции завершения.** В `finish_ride` после закрытия сегмента и чека — `flush`,
`send_receipt`, `commit`. Идемпотентный повтор возвращает чек до этой ветки, а параллельные
завершения упираются в `FOR UPDATE` на поездке и видят её уже завершённой. Событие `email.sent`
шлётся из роутера после `publish_ride_change`, письмо для события читается по `dedup_key`, а не
возвращается из сервиса: сервис остаётся чистой функцией над сессией.

**Деньги на фронте — строка как есть.** В дизайне предполагалось `formatMoney(parseMoney(s))` для
единообразия; при реализации от этого отказались: сервер уже отдаёт `"7.50"`, а любое
преобразование — лишний шанс разойтись. `displayMoney(amount, currency)` — конкатенация, без
арифметики, тест это закрепляет. Клиентская оценка осталась только у текущей поездки и подписана
как оценка.

**Хуки без setState в эффекте.** oxlint (`react/set-state-in-effect`) запретил синхронный
`setState` в `useEffect`; загрузка кабинета и почты сделана через `fetch().then(setState)` с
флагом отмены, отметка «прочитано» — функциональным `setState`. Состояние хуков ключуется
`userId`, как у брони и поездки: при смене пользователя в той же вкладке чужие письма не мелькают.

**Транслитерация.** Адрес `aybek@example.invalid` (не `aibek`): таблица транслитерации даёт «й» → «y»;
тест исправлен под таблицу, а не наоборот. `RUF001/002/003` (кириллица в строках) отключены в ruff:
русские строки в письмах и тестах намеренные.

**Сквозная проверка** (стек из чистого тома, Playwright, `feature/day5-mailbox`):
регистрация → бронь → старт → пауза → кабинет показывает текущую поездку («на паузе · с 23:29»,
оценка) → продолжить → «Завершить» внутри зоны: чек `0.68 KGS`, на кнопке «Почта» появился `· 1`
по событию `email.sent`; повторный `POST /rides/{id}/finish` — 200 с тем же чеком, писем в
